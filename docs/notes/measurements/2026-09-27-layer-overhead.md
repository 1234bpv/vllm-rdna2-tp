# Е6.2: операції шару та кандидати на злиття

Джерела: PP-профіль 26.09 (`logs/e5.2-correlated-2026-09-27.json`)
та короткий TP=2 27.09 (`logs/e6-tp-correlated-2026-09-27.json`).
Обидва розібрано `tests/tools/decode_step_breakdown.py` за HIP correlation.
У TP взято 27 графів із пакетом 4; перший граф із пакетом 1 відкинуто.
Числа нижче — медіани сум тривалостей відповідних ядер у графі.

Звичайне зведення всього проміжку профілю TP непридатне для цього:
між першими кроками декоду воно захоплює додатковий префіл. Зокрема,
`gemm_w4a8_k` і `chunk_gated_delta_rule` з такого зведення не є
складниками чистого графа декоду N=4.

## Короткий TP=2, 300 токенів

На кожному ранзі — усі 64 шари: 48 GDN і 16 уваги. Для специфічних
операцій кількість викликів прямо збігається з числом відповідних шарів.
Спільні операції нормування, MLP та лінійні проєкції подано окремо:
їх середнє на 64 шари не приписує однакової вартості GDN і увазі.

| Операція | Викликів на граф | Ранг 0 / 1, мс на граф | Ранг 0 / 1, мкс на відповідний шар |
|---|---:|---:|---:|
| GDN recurrent | 48 | 1,227 / 1,165 | 25,55 / 24,28 |
| GDN causal conv update | 48 | 0,160 / 0,167 | 3,34 / 3,47 |
| int4 attention | 16 | 0,431 / 0,417 | 26,95 / 26,09 |
| reduce_segments | 16 | 0,609 / 0,582 | 38,09 / 36,39 |
| запис int4 KV | 16 | 0,107 / 0,105 | 6,69 / 6,58 |
| підготовка/квантування Q: abs, max, cast, round, clamp | 144 | 0,442 / 0,432 | 27,64 / 27,01 |
| норми та rsqrt-фузії, спільна група | 209 / 289 | 0,744 / 1,001 | 11,62 / 15,64 у середньому |
| MLP silu/mul | 64 | 0,263 / 0,164 | 4,10 / 2,56 |
| cat після розбиття лінійного шару | 64 | 0,209 / 0,208 | 3,27 / 3,25 |
| int4 лінійні проєкції | 320 | 24,215 / 23,894 | 378,36 / 373,34 у середньому |

Назви для групи Q наведено як операції, а не як окреме доведене місце
у вихідному Python-коді: частина загальних cast/clamp може обслуговувати
сусідні перетворення. Повні назви й кількості збережено в JSON, тому
оцінку можна уточнити без нового GPU-прогону.

Для порівняння, PP=3, пакет 2, 125k: GDN recurrent ≈23–24 мкс на шар,
conv ≈3,1–3,4 мкс. Увага зі зведенням ≈2,25–2,67 мс на шар; на довгому
контексті дрібні операції значно менш важливі за читання KV та лінійні.

## Що можна злити і скільки це потенційно дає

| Кандидат | GPU-час, який можна намагатися прибрати, мс на граф TP |
|---|---:|
| Запис частин down_proj одразу у спільний вихід замість cat | ≤0,21 |
| Злиття підготовки int8-Q (abs/max/cast/round/clamp) | ≤0,44 |
| Включення silu/mul в сусідню лінійну операцію | ≤0,26 |
| Подальше злиття норм і rsqrt-фузій | ≤1,00; це вся група, не реалістичний повний виграш |

Це верхні оцінки **усунутого часу перелічених ядер**, не обіцянка
наскрізного прискорення. Повністю прибрати всі чотири групи означало б
приблизно 1,8 мс на граф на повільнішій за ними стороні; реальний виграш
менший через необхідність виконувати арифметику й обмін даними.
Для масштабу, звичайний короткий прогін на чотирьох дає 98,527 ток/с,
тобто ≈40,6 мс на чотири токени; 1,8 мс — ≈4,5%. Це лише зіставлення
порядків величин: профіль і звичайний замір мають різні накладні витрати.
Ефект усунення проміжків між запусками окремо не виміряний.

Профіль також містить 129 host all-reduce на граф. Медіана їх суми
59,47 мс на ранзі 0 і 4,97 мс на ранзі 1; це включає очікування іншої
карти й вплив профайлера. Рахувати ці 59 мс як незалежну обчислювальну
накладну або додавати час обох рангів не можна.

**Рішення Е6.2:** перелік операцій і оцінки складено. Даних за ≥10%
наскрізного виграшу від злиття немає, тому окремий план реалізації
фузій поки не відкривається. Сталу 12,6 мс із попереднього розбору не
підтверджено як суму дрібних ядер. Оптимізація лінійного ядра Е6.1
залишається окремою незавершеною роботою.

## Уточнення мікростенда Е6.1

Поточна увага має вихідний gate: qkv на ранзі TP=2 —
`5120 → (2×24×256 + 2×4×256)/2 = 7168`, а не 4096.
Для GDN qkvz — 8192, gate_up — 17408. Стару форму 4096 залишено
додатковим контрольним випадком; бойову оцінку за нею не підмінюємо.
Мікростенд перевірятиме всі чотири форми на N=1…5.

У метаданих TP-профілю ROCm повідомляє `numSms=30/36`, хоча фізичних
CU у карт 60/72. Саме `multi_processor_count` передається в диспетчер
скінні-ядра. При аналізі порогів YTILE не слід підставляти 60/72:
це дає неправильний прогноз вибраної гілки.
