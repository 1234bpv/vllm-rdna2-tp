## 1. Керування вентиляторами

### Що виявлено

Плата **не має BMC/IPMI** (DMI type 38 порожній), тож `ipmitool` не застосовний.
Монітор апаратного стану — **Nuvoton NCT6779** на ISA 0xa20, драйвер `nct6775`
(вантажиться без `acpi_enforce_resources=lax`).

| Канал | Що робить |
|---|---|
| `pwm1` | ні на що не впливає — до нього нічого не підключено (DC-режим, 255) |
| **`pwm2`** | керує **обома** вентиляторами одночасно, роздільно їх не розвести |
| `pwm3/4/5` | тахометрів немає; чи є там вентилятори — перевіряти на слух |

Виміряна характеристика pwm2:

| PWM | RPM |
|---|---|
| 50 | ~770 |
| 60 | ~790 |
| 120 (заводське BIOS) | ~1100 |
| 170 | ~1440 |
| 255 | ~1850 |

**Перепідключення вентилятора в інший порт нічого не змінило** — тахо-сигналів
як було два, так і лишилось, і обидва так само реагують на pwm2.

### Датчикам плати вірити не можна

- `PECI Agent 0` занижує на ~13 °C (24 °C проти 37 °C у `coretemp`);
- `AUXTIN1/2/3` — непідключені термістори, показують сталі 107–112 °C;
- `PCH_*` — сталий 0 °C;
- `Vcore` — 1.82 V, що для E5 v3 неможливо (нестандартний дільник).

Все це приховано в `/etc/sensors.d/test-machine.conf`. Керування будується на
`coretemp` (`Package id 0` / `Package id 1`, crit 86 °C).

### Що встановлено

| Файл | Призначення |
|---|---|
| `/usr/local/sbin/fanctl` | демон керування |
| `/etc/default/fanctl` | крива та параметри |
| `/etc/systemd/system/fanctl.service` | автозапуск |
| `/usr/local/sbin/fan-identify` | пошук шумного вентилятора на слух |
| `/etc/sensors.d/test-machine.conf` | приховані хибні датчики |
| `/etc/modules-load.d/nct6775.conf` | автозавантаження драйвера |

`fancontrol` встановлений, але **вимкнений** (`systemctl disable fancontrol`):
він прив'язує до одного каналу PWM рівно одне джерело температури, а тут один
канал обдуває обидва процесори — потрібен максимум по двох пакетах.
У юніті стоїть `Conflicts=fancontrol.service`, щоб вони не билися за канал.

### Крива (за замовчуванням)

```
CPU  <=40 °C -> pwm 60   (~790 RPM)
CPU   70 °C+ -> pwm 255  (~1850 RPM)
GPU  <=50 °C -> pwm 60
GPU   85 °C+ -> pwm 255
```
Береться максимум із двох. Угору реакція миттєва, вниз — по 8 одиниць за 5 с,
щоб не гуділо ривками. Перевірено під навантаженням на 72 потоки:
33 °C → pwm 60; 49 °C → 118; 57 °C → 170; спуск плавний.

Тюнінг — у `/etc/default/fanctl`, далі `sudo systemctl restart fanctl`.
Тихіше в простої: `PWM_MIN=50`. **Нижче 40 не опускати — вентилятори зриваються.**

Fail-safe: при зупинці служби канал повертається під BIOS Smart Fan IV
(`pwm2_enable=5`), тобто вентилятори не лишаються на мінімумі.

### Якщо шумний вентилятор — не з цієї пари

```bash
sudo fan-identify        # усі канали по черзі
sudo fan-identify 3 4 5  # тільки ті, де немає тахометра
```
Кожен канал на 10 с скидається до мінімуму; коли шум зникне — це він.
Якщо жоден канал не впливає, вентилятор живиться не від плати (molex/PSU) —
лікується тільки заміною або перехідником зі зниженою напругою.

## 2. Гальмування інтерфейсу після встановлення другої карти

### Причина

Xorg зробив головним екраном карту, до якої **не підключений монітор**:

```
Provider 0: cap 0x9, Source Output, Sink Offload @ 04:00.0   ← рендерить
Provider 1: cap 0x6, Sink Output, Source Offload @ 07:00.0   ← монітор тут
```

Це PRIME output offload: кожен кадр малюється на 04:00.0 і копіюється через
PCIe на 07:00.0 для виводу. На X11 цей шлях дуже повільний.

Xorg обирає primary за boot-VGA, а VGA-арбітраж належить 04:00.0
(`vgaarb: ... owns=io+mem` у dmesg).

### Виправлення А — перевтикнути кабель (рекомендовано)

Перекласти монітор у карту **04:00.0**. Тоді boot-VGA і карта виводу збігаються,
жодних конфігів. **Бонус: ви побачите екран POST і зможете зайти в BIOS** —
зараз POST іде на 04:00.0, тому з монітором на 07:00.0 BIOS для вас невидимий.
А він потрібен (див. §3).

### Виправлення Б — примусово задати primary в Xorg

Якщо монітор має лишитися на 07:00.0, створити
`/etc/X11/xorg.conf.d/10-primary-gpu.conf`:

```
Section "Device"
    Identifier "AMD-primary"
    Driver     "amdgpu"
    BusID      "PCI:7:0:0"
EndSection
```

Потім перезапустити сесію. Мінус: BusID зашитий жорстко — при переставлянні
карт у інші слоти файл треба правити або видаляти, інакше X не підніметься.
Відкат із TTY (Ctrl+Alt+F3): `sudo rm /etc/X11/xorg.conf.d/10-primary-gpu.conf`.

Перевірка після виправлення — у `xrandr --listproviders` карта з монітором
має бути `Source Output`:
```bash
xrandr --listproviders
```

## 3. Що змінити в BIOS

### NUMA — увімкнено, працює (2026-08-17)

```
available: 2 nodes (0-1)
node 0 cpus: 0-17,36-53    node 0 size: 64309 MB
node 1 cpus: 18-35,54-71   node 1 size: 64450 MB
node distances:  0:10  1:21          ← 21 = через QPI
SRAT: 4440 байт, ACPI v03 ALASKA A M I
```

Слот з відеокартою — **на сокеті 0**: `numa_node=0`, `local_cpulist = 0-17,36-53`.
Отже для інференсу:
```bash
numactl --cpunodebind=0 --membind=0  llama-server ...
```
Перевірити прив'язку після кожної зміни слота:
```bash
cat /sys/bus/pci/devices/0000:04:00.0/numa_node
cat /sys/bus/pci/devices/0000:04:00.0/local_cpulist
```

### Стан на 2026-08-17 після змін у BIOS

| Опція | Стан | Як перевірено |
|---|---|---|
| Above 4G Decoding | **Enabled** | MMIO на `0x380000000000`, BAR 16 ГБ |
| Resizable BAR у BIOS | вимкнено — **і не потрібно** | `amdgpu` змінює розмір BAR сам |
| Частота пам'яті | 2133 MT/s (стеля платформи) | усі 8 планок |
| NUMA | **не працює: BIOS не публікує SRAT** | таблиці ACPI |

**ReBAR у BIOS на Linux вмикати не треба.** Достатньо Above 4G Decoding —
драйвер `amdgpu` при завантаженні сам звільняє маленький BAR і призначає повний:
```
amdgpu 0000:04:00.0: BAR 0 [mem 0x383fe0000000-0x383fefffffff]: releasing   ← 256 МБ
amdgpu 0000:04:00.0: BAR 0 [mem 0x380000000000-0x3803ffffffff]: assigned    ← 16 ГБ
[drm] Detected VRAM RAM=16368M, BAR=16384M
```
Видима для CPU VRAM зросла з 256 МБ до 15 GiB на обох картах.

### Node Interleaving → Disabled (важливо)

Зараз:
```
available: 1 nodes (0)
node 0 cpus: 0..71
node 0 size: 128663 MB
```

Обидва сокети склеєні в один NUMA-вузол, тобто пам'ять інтерлівиться між
процесорами і приблизно половина звернень іде через QPI. Наслідки:

- **CPU-інференс втрачає** — `llama.cpp --numa distribute` і `numactl` не мають
  за що зачепитися;
- `numa_node` у обох GPU = **-1**, тобто неможливо визначити, який слот до якого
  процесора підключений;
- ваш дослідницький план по TP (крос-сокетна точка свіпу, `lstopo`,
  `numa_node` як незалежна змінна) у такому стані **нездійсненний**.

**Уточнення після перевірки ACPI: справа не в інтерлівингу.**
У списку таблиць ACPI **немає SRAT** — тієї самої таблиці, якою прошивка
описує прив'язку пам'яті та пристроїв до сокетів:

```
$ ls /sys/firmware/acpi/tables/
APIC DMAR DSDT dynamic FACP FACS FIDT FPDT HPET MCFG NITR PRAD SSDT1 SSDT2 SSDT3 UEFI WDDT
$ dmesg | grep -i numa
[    0.000000] No NUMA configuration found
```

Якби був увімкнений Node Interleaving, BIOS зазвичай усе одно публікував би
SRAT з одним доменом. Тут таблиці немає взагалі — прошивка не повідомляє
топологію в принципі. Тому в меню може просто не бути відповідної опції.

Де шукати (назви з Intel RC для Grantley/C612):
- `Advanced` → `Chipset Configuration` → `North Bridge` → `Memory Configuration`
  → **`NUMA`** / `NUMA Optimized`
- поруч: `Socket Interleave Below 4GB`, `Memory Interleave Mode`,
  `Channel Interleaving`, `Rank Interleaving`
- `North Bridge` → `QPI Configuration` → `QPI General Configuration`
  → `Cluster On Die (COD)`

На цих платах підменю `Chipset Configuration` зазвичай **приховане**. Варіанти:
комбінації на головному екрані (`Ctrl+F1`, `Alt+F` — ненадійно) або модифікований
BIOS із репозиторіїв у нотатках міграції, який відкриває приховані опції.
Спершу варто прочитати їхній changelog: якщо ця прошивка взагалі не вміє SRAT,
жодна опція не допоможе.

**Що працює без SRAT:** топологія ядер видима (`lscpu -p=CPU,SOCKET`,
36 потоків на сокет), тож прив'язка **потоків** через `taskset` можлива.
Некерованим лишається лише розміщення **пам'яті**.

#### Обидві GPU — на сокеті 0

```
-+-[0000:00]-+-02.0-[02-04]--...--[04]--+-00.0     ← RX 6900 XT
 |           +-03.0-[05-07]--...--[07]--+-00.0     ← RX 6800 XT
 +-[0000:7f]  (uncore сокета 0)
   [0000:80]  лише 4 службові функції, жодного PCIe-моста
```

Наслідки після ввімкнення NUMA:

- обидві карти отримають `numa_node=0`; оптимальна прив'язка для інференсу —
  `numactl --cpunodebind=0 --membind=0` (36 потоків, **64 GB** локальної пам'яті);
- сокет 1 (36 потоків + 64 GB) стає віддаленим: корисний для чисто-CPU задач,
  але не для годування відеокарт;
- **процес, прив'язаний до вузла 0, побачить 64 GB, а не 128.** Для інференсу на
  GPU це неважливо (ваги у VRAM), але для великої CPU-моделі треба
  `numactl --interleave=all` — це відтворює поточну поведінку на вимогу.

⚠️ **Для §4 статті:** крос-сокетна точка свіпу під питанням — на шині сокета 1
зараз немає жодного PCIe-порту. Можливо, всі слоти розведені на CPU1, а можливо,
BIOS ховає порожні порти. Перевіряється переставлянням карти в інший слот
із наступним `lspci -s 80:`.

### Above 4G Decoding → Enabled, потім Resizable BAR → Enabled

**Виміряно 2026-08-17: Above 4G Decoding зараз ВИМКНЕНО.** У `/proc/iomem` немає
жодного діапазону вище 4 ГБ. Карти піднялися лише тому, що їхні BAR — по 256 МБ
і вміщуються під 4 ГБ.

Обидві карти підтримують ReBAR до 16 ГБ:
```
BAR 0: current size: 256MB, supported: 256MB 512MB 1GB 2GB 4GB 8GB 16GB
```
але зараз CPU бачить лише 256 МБ із 15 GiB (`mem_info_vis_vram_total`).

**Порядок увімкнення строго такий** — два BAR по 16 ГБ = 32 ГБ MMIO,
які фізично нікуди покласти без Above 4G:

1. `Above 4G Decoding` → Enabled → завантажитись → перевірити;
2. `Resizable BAR` → Enabled → завантажитись → перевірити.

Перед цим знайти на платі перемичку **Clear CMOS**: якщо BIOS не зможе роздати
вікна, не буде ні зображення, ні POST, і скинути налаштування можна лише нею.

Перевірка після кожного кроку:
```bash
# має з'явитися MMIO вище 4 ГБ
sudo awk -F- '{ if (strtonum("0x"$1) >= 4294967296) print }' /proc/iomem | head
# BAR 0 має стати 16GB, vis_vram — рівним vram
sudo lspci -vv -s 04:00.0 | grep -A2 "Resizable BAR"
cat /sys/class/drm/card0/device/mem_info_vis_vram_total
```

## 3a. BIOS не показує зображення (Linux при цьому працює)

З'явилося одразу після ввімкнення Above 4G Decoding.

**Карта й кабель тут ні до чого** — прошивка мала робочий графічний вивід на
момент передачі керування ядру:
```
[drm] Initialized simpledrm 1.0.0 for simple-framebuffer.0
```
`simple-framebuffer` створюється з фреймбуфера, який віддає UEFI GOP. Отже GOP
працював. Монітор підключений до `04:00.0`, а `boot_vga=1` саме в неї — тобто
POST іде на правильну карту.

Що пробувати, за спаданням шансів:

1. **Перекласти монітор у DisplayPort.** На цій карті всі три DP вільні, зайнятий
   лише HDMI. Прошивка часто ініціалізує лише один конектор, і зазвичай це DP.
2. Тиснути `Del`/`F2` з моменту подачі живлення — setup може бути активним,
   навіть якщо не видно.
3. Монітор може не встигати синхронізуватися: вікно запрошення коротке,
   а Linux стартує на кілька секунд пізніше — тому його видно.

### Вхід у setup без вгадування моменту

Прошивка підтримує вхід у setup через EFI-змінну — перевірено:
```
$ sudo od -An -tx1 /sys/firmware/efi/efivars/OsIndicationsSupported-*
 06 00 00 00 01 00 00 00 00 00 00 00
                ^^ біт0 = EFI_OS_INDICATIONS_BOOT_TO_FW_UI
```
Отже працює:
```bash
systemctl reboot --firmware-setup
```
Це знімає проблему «не встиг натиснути Del». Якщо після цього екран усе одно
чорний — проблема саме у виводі зображення, а не у вході. Прапорець одноразовий:
щоб вийти, достатньо вимкнути живлення довгим натисканням і увімкнути знову.

### Console redirection через послідовний порт

На платі два справжніх 16550A:
```
00:03: ttyS0 at I/O 0x3f8 (irq = 4)
serial8250: ttyS1 at I/O 0x2f8 (irq = 3)
```
Якщо в BIOS увімкнено `Console Redirection` (на серверних платах часто типово),
меню setup видно в терміналі з іншої машини: null-modem або USB-serial,
`screen /dev/ttyUSB0 115200` (8N1). Для плати без вбудованого відео це штатний
спосіб адміністрування.

### Скидання CMOS — не глухий кут, але цикл

Перемичка Clear CMOS повертає заводські значення: Above 4G вимикається,
зображення BIOS з'являється. Але щойно ви знову ввімкнете Above 4G, екран
зникне знову. Тому скидання має сенс лише як **один підхід із готовим списком**:
зайти, змінити все потрібне (`NUMA`, `Above 4G Decoding`, і що ще знадобиться),
зберегти — і далі жити без зображення BIOS.

Список змін варто написати **до** скидання.

## 3b. Споживання в простої та C6

### Розбір споживання (виміряно 2026-08-17)

Одна карта, до і після ввімкнення C6:

| Складова | Ватт | Джерело |
|---|---|---|
| Два пакети CPU | 39.6 → **28.0** з C6 | RAPL / turbostat |
| DRAM (8 планок) | 20.9 | RAPL |
| Відеокарта | 12 | hwmon amdgpu |
| **Виміряно разом** | **72.5 → 60.9** | |
| PCH, два комутатори PCIe, NVMe, вентилятори, втрати VRM і БЖ | ~57 | різниця до 130 Вт |

Фінальна конфігурація — дві карти, C6 увімкнений:

| Складова | Ватт |
|---|---|
| пакет 0 (тримає root-порти обох GPU) | 21.4 |
| пакет 1 (без PCIe-пристроїв) | 14.3 |
| DRAM | 21.0 |
| GPU разом (RX 6800 + 6800 XT у простої) | 18 |
| **Виміряно разом** | **74.7** |

Друга карта коштує ~8 Вт у пакеті 0 (root-порт та IIO входять у той самий
домен живлення) плюс власні ~9 Вт. C6-присутність при цьому 94.5 % —
не деградувала, приріст саме від карти.

Процесори з пам'яттю за власними лічильниками дають 61 Вт, тож **40 Вт від
розетки для цієї конфігурації недосяжні** — та давня цифра стосувалася іншої
збірки. Крім того, Chieftec 1450 Вт на 130 Вт працює на 9 % потужності: 80 Plus
Gold не сертифікується нижче 10 %, там втрачається 15–20 Вт, і це не лікується.

### Турбобуст розблокований

```
MSR_TURBO_RATIO_LIMIT (0x1AD) = 0x2424242424242424
```
Кожен байт `0x24` = множник 36 → **3.6 ГГц на будь-якій кількості ядер**
(у стоку множники спадали б до ~28 на всіх ядрах). База — 2300 МГц.

**Вимикати турбо для економії немає сенсу:** у простої `Avg_MHz = 23` при
`Busy% = 1.35`, тобто він не витрачає нічого. Коштує лише під навантаженням.

### C6: чому працює зараз, хоч у BIOS зависав

```
MSR_PKG_CST_CONFIG (0xE2) = 0x8401
  → C-state limit = 1 (C2)
  → біт CFG lock  = 1   (регістр замкнений, з Linux не змінити)
```

BIOS обмежив **пакетний** C-стан до C2 і замкнув регістр. Конфлікт
розблокованого турбо з C6 живе саме в пакетних станах, де PCU узгоджує uncore
і турбо-множники. Цей шлях закритий замком, тому вмикається лише C6 **на рівні
ядер** — інша конфігурація, ніж та, що зависала:

| | Пакетний стан | Ядра | Результат |
|---|---|---|---|
| C6 через BIOS | PC6/PC7 | C6 | зависання при завантаженні |
| C6 через sysfs (зараз) | замкнено на PC2 | C6 | 28 Вт, стабільно |

Апаратно C6 не був заблокований — його вимикав драйвер `intel_idle`.

### Перевірка стабільності — пройдена

`sudo cstate-soak` (30 циклів простій↔усі ядра, 25 циклів одне ядро на 3.6 ГГц,
60 с усі ядра без перерви):

```
входів у C6 за тест: 699963
рядків MCE: 0 -> 0
пік температури: 60 C (crit 86)
РЕЗУЛЬТАТ: система вижила, помилок немає
```

Увімкнено постійно: `systemctl enable deep-cstates`.
Відкат: `sudo /usr/local/sbin/deep-cstates disable` (+ `systemctl disable`).

Додані файли: `/usr/local/sbin/deep-cstates`,
`/etc/systemd/system/deep-cstates.service`, `/usr/local/sbin/cstate-soak`.

### ⚠️ Вимкнено на час досліду (23.08)

`deep-cstates` **зупинено й знято з автозапуску** — це НЕ «забули ввімкнути».
Причина: з 18.08 машина повторно зависає на ПРОСТОЇ, а C6 увімкнено саме
17.08. Три останні завантаження (`-1`, `-2`, `-3`) обриваються без жодного
рядка вимкнення, банки MCA чисті, у журналі — лише фонова балаканина
`warp-svc`. Тобто це раптовий обрив живлення/скидання, а не паніка ядра.
Соак `cstate-soak` цього не ловив: він ганяв переходи простій↔навантаження
циклами, а зависання стається після ДОВГОГО безперервного простою.

Це другий підозрюваний після даунвольта (`VOLT_OFFSET=0` з 21.08 — зависання
не зникли, тож перша підозра слабшає). Змінюємо по одному: якщо кілька діб
без зависань — винен C6.

Повернути:

```bash
sudo systemctl enable --now deep-cstates
```

Перевірити стан без systemd:

```bash
cat /sys/devices/system/cpu/cpu0/cpuidle/state4/disable   # 1 = C6 вимкнено
```

Побічно: юніт мав водночас `After=multi-user.target` і
`WantedBy=multi-user.target` — рівно той візерунок, що 19.08 дав кільце
впорядкування й тихо викинув `gpu-thermal-guard`. `After=` **прибрано
одразу 23.08**, щоб при поверненні C6 про це не забути; лишилися тільки
неявні залежності (`sysinit.target`, `basic.target`).

## 3c. Заборона засинання (плата не має S3)

`ACPI: PM: (supports S0 S4 S5)` і `/sys/power/mem_sleep = [s2idle]` —
**S3 (suspend-to-RAM) на цій платі відсутній**. Тому будь-який запит «заснути»
відкочується на `s2idle`, який без прошивкової підтримки вішає машину.
Це і є причина зависань приблизно через 15 хвилин простою.

Зроблено:
```bash
systemctl mask sleep.target suspend.target hibernate.target \
                hybrid-sleep.target suspend-then-hibernate.target
```
`/etc/systemd/logind.conf.d/99-no-suspend.conf`: `IdleAction=ignore`,
`HandleSuspendKey=ignore`, `HandleHibernateKey=ignore`, `HandleLidSwitch=ignore`.

`~/.config/powermanagementprofilesrc` переписано: прибрано групи
`DimDisplay`, `DPMSControl`, `SuspendSession` в усіх профілях;
у `SpecialBehavior` виставлено `noSuspend=true`, `noScreenManagement=true`.
Бекап: `powermanagementprofilesrc.bak-*`.

Перевірка: `sudo systemctl suspend` → `Call to Suspend failed: Access denied`.
Відкат: `systemctl unmask sleep.target suspend.target ...`

⚠️ `kwriteconfig5` **не вміє видаляти групи** (`Internal KConfig error:
cannot mark groups as deleted`) — файл треба правити напряму.

⚠️ Збірка виводить `UI: download dist.tar.gz from b1 failed` — не завантажився

⚠️ У свіжому master `llama-cli` **завжди** інтерактивний; `-no-cnv` більше не

на stdin дає нескінченний цикл `>` (за 10 хв нагенерував лог на 2 ГБ).

### Модель Qwen3.8-27B (arch `qwen35`)

`~/models/run-qwen3.8-27b.sh` — сервер на `127.0.0.1:8090`
(8080 зайнятий сервером LM Studio), OpenAI-сумісний API.

Штатний режим — **контекст 131072, KV-кеш `q8_0`, MTP увімкнено**.
Реальний промпт 9320 токенів + 325 згенерованих, VRAM 30,6 ГБ із 34,3 ГБ:

| Метрика     | без MTP    | з MTP (штатно) |
|-------------|------------|----------------|
| Prompt eval | 409,4 t/s  | 270,8 t/s      |
| Генерація   | 16,6 t/s   | **27,3 t/s**   |
| Час старту  | ~10 с      | ~10 с          |

### MTP (спекулятивне декодування)

У моделі є MTP-шар (`nextn_predict_layers = 1`). llama.cpp вміє його
використовувати — `--spec-type draft-mtp`, окрема draft-модель не потрібна:
контекст будується проти самої моделі, `load_mtp` вмикається автоматично.
Прийняття чернеток 60–70%, середня довжина прийнятого 2,8–3,1 токена.

**Якість не страждає** — чернетки перевіряються цільовою моделлю, розподіл на
виході тотожний звичайному декодуванню. Ціна — VRAM (~1,4 ГБ) і швидкість
обробки промпту.

⚠️ **MTP коштує 34% prompt eval**, бо чернетковий контекст мусить прогнати той
самий промпт через свою голову. Точка беззбитковості:

```
MTP додає  +1,25 мс на токен промпту
MTP економить 23,4 мс на токен генерації
→ вигідно, поки промпт < ~19× довжини відповіді
```

Для агентної роботи це майже завжди вигідно, бо `llama-server` кешує префікс:
у циклі кожен хід обробляє лише нову частину контексту, а генерує повну
відповідь. Для разової обробки величезного тексту з короткою відповіддю —
навпаки. Вимикається без перезбірки: `MTP=0 ~/models/run-qwen3.8-27b.sh`.

### Контекст і квантизація KV-кешу

KV-кеш дорогий: `16 повних шарів × (256+256) × 4 KV-голови × 2 Б = 64 КіБ на
токен` у f16. Квантизація KV вимагає flash attention (`-fa 1`).

| ctx  | KV f16   | KV q8_0  | KV q4_0 |
|------|----------|----------|---------|
| 32k  | 2,0 ГіБ  | 1,1 ГіБ  | 0,6 ГіБ |
| 128k | 8,0 ГіБ  | 4,3 ГіБ  | 2,3 ГіБ |
| 160k | 10,0 ГіБ | 5,3 ГіБ  | 2,8 ГіБ |
| 256k | 16,0 ГіБ | 8,5 ГіБ  | 4,5 ГіБ |

Що реально влазить разом із вагами (18,8 ГіБ) і mmproj (0,86 ГіБ):

| Конфігурація              | Генерація | VRAM    | Статус |
|---------------------------|-----------|---------|--------|
| **131072 + q8_0 + MTP**   | 27,1 t/s  | 29,4 ГБ | штатна |
| 163840 + q4_0 + MTP       | 30,4 t/s  | 28,8 ГБ | працює |
| 163840 + q8_0, без MTP    | 19,0 t/s  | 30,6 ГБ | працює |
| 163840 + q8_0 + MTP       | —         | —       | ❌ OOM |
| 262144 + q4_0 + MTP       | —         | —       | ❌ OOM |
| 262144 + q8_0             | —         | —       | ❌ OOM |

Контекст понад 131072 з `q8_0` і MTP одночасно не влазить; 98304 і 114688
дають ту саму швидкість, тож 131072 — максимум без втрат.

### Чому LM Studio не завантажив цю модель

```
failed to create MTP context: failed to allocate compute pp buffers
```

Дві причини, обидві про VRAM:

1. **KV-кеш.** `context_length` у метаданих — 262144. Архітектура гібридна
   (`full_attention_interval = 4`), повних шарів уваги лише 16 з 64, але вони
   важкі: `key_length = value_length = 256`, 4 KV-голови.
   `16 × (256+256) × 4 × 2 Б = 64 КіБ на токен` → на 262k це 16 ГіБ самого
   лише кешу. На 32k — 2 ГіБ, на 128k — 8 ГіБ.
2. **MTP.** `nextn_predict_layers = 1`; під нього піднімається окремий
   контекст для спекулятивного декодування — другий комплект compute-буферів,
   найбільший з яких пропорційний словнику (248320 × n_ubatch × 4 Б ≈ 0,5 ГБ).

⚠️ Рядок `failed to create MTP context` — це повідомлення **самого llama.cpp**
(`common/speculative.cpp`), а не LM Studio. Власної реалізації MTP у LM Studio
немає, він лише викликав цей код. Лікується меншим контекстом (у llama.cpp він
задається явно, а не береться з метаданих) або `MTP=0`.

Без `--spec-type draft-mtp` llama.cpp MTP-шар просто ігнорує —
`model has unused tensor blk.64.nextn.*` у логу.

### Квантизація KV-кешу: заміряна якість і швидкість

Perplexity на wikitext-2, `-c 4096 --chunks 20`, той самий корпус і зерно.
Швидкість — `llama-bench -p 2048 -n 128`.

| KV            | PPL              | Δ до f16 | pp2048    | tg128 |
|---------------|------------------|----------|-----------|-------|
| f16 (базова)  | 5,9542 ± 0,0721  | —        | 402,7     | 18,99 |
| q8_0          | 5,9490           | −0,09%   | 401,9     | 18,61 |
| q8_0 лише K   | 5,9577           | +0,06%   | —         | —     |
| q8_0 лише V   | 5,9347           | −0,33%   | —         | —     |
| q5_1          | 5,9499           | −0,07%   | **88,2**  | 16,86 |
| q4_0          | 5,9987           | +0,75%   | 402,7     | 18,51 |

**Головне про швидкість:** ⚠️ `q5_1` обвалює обробку промпту в **4,6 раза**
(402 → 88 t/s) — для нього немає ядра flash-attention на ROCm, іде повільний
запасний шлях. `q8_0` і `q4_0` мають повноцінні ядра й коштують ~2% генерації.
**`q5_1` не використовувати.**

**Головне про якість:** усі відхилення менші за похибку вимірювання (±0,072),
тобто на 20 чанках perplexity не розрізняє навіть `q4_0`. Єдиний тип, що зсунув
її вгору послідовно, — `q4_0` (+0,75%).

⚠️ **Perplexity — слабкий інструмент для цього питання.** Вона усереднює по
всьому тексту й не ловить саме те, що помітно суб'єктивно: дотримання
інструкцій, міркування, робота з довгим контекстом. Це підтверджують і
дослідження — деградація вирівнювання при квантизації KV проявляється при
низькій PPL. Тому «на perplexity не видно» ≠ «різниці немає».

Практичний висновок: `q8_0` брати спокійно, `q4_0` — лише коли інакше не
влазить, і бажано перевірити на своїх задачах.

Чому K чутливіший за V (за літературою): помилка в K проходить через softmax
і впливає на ваги уваги всіх позицій, тоді як V лише лінійно змішується.
Плюс у K є канали-викиди з нормою в 10–100 разів більшою за медіану, які
поблочна квантизація по 32 значення обробляє погано. На цій моделі різниця
K-only проти V-only (+0,06% проти −0,33%) в той самий бік, але обидві в межах
шуму.

### ⚠️ Моделі тримати на NVMe, не на зовнішньому HDD

HDD підключений через `usb-storage` (BOT), а не `uas`, і дає **32 МБ/с** при
лінку 5 Гбіт/с (`hdparm -t /dev/sdc` — читання сирого пристрою, тобто ntfs3
ні до чого). Завантаження 19-ГБ моделі звідти — понад 10 хвилин, а `mmap`
під час інференсу через такий канал непридатний.

Активні моделі — у `~/models` на NVMe (звідти старт ~10 с), HDD —
холодний архів.

## 3g. Даунвольт і обмеження частот GPU (2026-08-18)

Мета — зрізати споживання під інференсом. Усе міряно `llama-bench` на
Qwen3.8-27B (`-p 2048 -n 128 -r 3`) з паралельним семплінгом `rocm-smi`.

### Підсумок

**Штатно: SCLK ≤ 1900 МГц, зсув напруги −30 мВ, MCLK стоковий.**
Споживання 491 → 288 Вт (**−41%**) при втраті 3% генерації.

Застосовується автоматично: `/etc/systemd/system/gpu-tune.service` →
`/usr/local/sbin/gpu-tune.sh`. OverDrive **не переживає перезавантаження**,
тому без служби налаштування злітають.

```bash
sudo systemctl disable --now gpu-tune.service   # відкат
sudo reboot                                     # або просто перезавантажитись
```

### ⚠️ Головна знахідка: MCLK чіпати не можна

Спроба підняти пам'ять до 1050 (= «2100» у конвенції Adrenalin, там прийнято
вдвічі більше число) **обвалила генерацію на 26%**:

| MCLK (Linux / Windows) | tg128     | pp2048 |
|------------------------|-----------|--------|
| 1000 / 2000 (сток)     | **18,98** | 402    |
| 1025 / 2050            | 14,03     | 400    |
| 1050 / 2100            | 14,00     | 399    |

Це відома на RX 6000 зміна таймінгів пам'яті: за порогом контролер переходить
на слабший набір, і виграш від частоти з надлишком з'їдається. Особливості:

- деградація **стрибком**, а не плавна — 1025 і 1050 дають однакове число;
- на `pp` не впливає взагалі (він упирається в ядро), тільки на `tg`;
- запис `m 1 1000`, тобто стокового значення через OD-таблицю, нешкідливий —
  справа саме у величині;
- ⚠️ **на Windows поріг вищий** — там таймінги тримаються десь до 2098, тому
  «2100» вважається безкоштовним розгоном. У Linux ламається вже на 2050.
  Причина розбіжності не з'ясована (інша таблиця в драйвері або SMU).

Крім того, зависання системи, після якого довелося перезавантажуватись,
сталося саме на конфігурації з розігнаною пам'яттю. Не доказ, але узгоджується.

### Крива «частота ядра ↔ споживання» (−30 мВ, MCLK стоковий)

| SCLK        | pp2048 | tg128 | Вт  | t/s на ват |
|-------------|--------|-------|-----|------------|
| сток ~2300  | 470,1  | 19,56 | 491 | 0,040      |
| 2200        | 458,2  | 15,31 | 412 | —          |
| 2100        | 438,2  | 15,01 | 358 | —          |
| **1900**    | 401,8  | 18,98 | 288 | 0,066      |
| 1700        | 361,5  | 18,56 | 258 | 0,072      |
| 1400        | 300,9  | 17,65 | 232 | 0,076      |

(Рядки 2200 і 2100 міряні ще з MCLK 1050, тому їхній `tg` занижений — саме
ця аномалія й вивела на проблему з таймінгами.)

Два різні режими роботи:

- **`pp` (обробка промпту)** масштабується з частотою ядра майже лінійно —
  це щільна матрична арифметика, впирається в обчислення;
- **`tg` (генерація)** майже не залежить від частоти: 1400 → 1900 МГц дають
  17,65 → 18,98 t/s. Вона впирається в пропускну здатність пам'яті.

Тому дешевше за все економити саме на ядрі. Якщо `pp` не критичний, **1700 МГц
дає −47% споживання при −5% генерації** — краща точка за ефективністю.

### Технічні деталі

- `pp_od_clk_voltage` доступний, бо `ppfeaturemask = 0xfff7ffff` містить біт
  `PP_OVERDRIVE_MASK` (0x4000). Додавати `amdgpu.ppfeaturemask` у GRUB не треба.
- ⚠️ **Нумерація карт інвертована.** `rocm-smi` GPU0 (RX 6800, `0000:04:00.0`)
  = `card1`, а GPU1 (RX 6800 XT, `0000:07:00.0`) = `card0`. Перевіряти через
  `rocm-smi --showbus` і `readlink /sys/class/drm/cardN/device`.
- OD пишеться лише в режимі `manual`, але **діє й після повернення в `auto`**,
  а `auto` потрібен, щоб карта сама тримала частоту під навантаженням.
- `-50 мВ` замість `-30 мВ` не дав нічого: 399,2 проти 399,4 `pp` і 293 проти
  295 Вт. Глибше не пробувалось.
- У простої: GPU0 31 Вт (тримає монітор), GPU1 6 Вт.

## 4. Стан заліза (виміряно 2026-08-17)

### Відеокарти

| Шина | Карта | CU | Ліміт | VRAM | numa | Роль |
|---|---|---|---|---|---|---|
| 04:00.0 | **RX 6800** (rev c3) | 60 | 203 Вт | 15 GiB | 0 | primary, рендер, монітор (DP-2) |
| 07:00.0 | **RX 6800 XT** NITRO+ (rev c1) | 72 | 289 Вт | 15 GiB | 0 | вільна під обчислення |

Обидві `gfx1030`, драйвер `amdgpu`, SMU ініціалізується без помилок,
ReBAR 16 ГБ, видима VRAM 15 GiB, Gen4 x16 до комутатора.

**Як ідентифікувати карту правильно.** Ні `lspci`, ні subsystem ID тут не
надійні: subsystem ID у 04:00.0 показує «Radeon RX 6900 XT» — рядок у VBIOS
перешитий, що звична річ на вживаних картах. Однозначна ознака — **кількість
Compute Units** (RX 6800 = 60, 6800 XT = 72, 6900 XT = 80):
```bash
rocminfo | grep -E "Marketing Name|Compute Unit:"
cat /sys/bus/pci/devices/0000:04:00.0/hwmon/hwmon*/power1_cap   # 203 W vs 289 W
```
Монітор стоїть на слабшій карті (RX 6800) — це правильно: сильніша лишається
цілком вільною під інференс.

### PCIe

Обидві карти — за комутаторами, на **різних** root-портах:

```
00:02.0 → 02:00.0 → 03:00.0 → 04:00.0
00:03.0 → 05:00.0 → 06:00.0 → 07:00.0
```

| Ділянка | Швидкість |
|---|---|
| GPU ⟷ комутатор | 16 GT/s x16 (Gen4) |
| комутатор ⟷ CPU | 8 GT/s x16 (Gen3, стеля Haswell-EP) ≈ 15.75 ГБ/с |

Аплінк карти не ділять — кожна має повну смугу Gen3 x16.
Не переплутати: `current_link_speed` у sysfs показує **локальний** лінк карти
(Gen4 до комутатора), а не наскрізну смугу до пам'яті.

### Пам'ять

8× 16 GB «atermiter», рівно розкладені: C1/C2/D1/D2 на CPU1, G1/G2/H1/H2 на CPU2
(2 планки на канал, dual-rank).

| | |
|---|---|
| SPD модулів | 3200 MT/s |
| Працюють на | **2133 MT/s** |

**2133 — це стеля платформи, а не недокрут BIOS.** Контролер пам'яті
Haswell-EP (E5-2699v3) офіційно підтримує максимум DDR4-2133; XMP на цій
платформі не діє. Частота 3200 із SPD тут недосяжна в принципі.

Реальне вузьке місце — не частота, а **2 канали на процесор**:
```
2 канали × 2133 MT/s × 8 Б = 34.1 ГБ/с на сокет
                             68.3 ГБ/с сумарно (лише з NUMA-обізнаним розміщенням)
```
Звичайна плата під E5 v3 дала б 4 канали = 68 ГБ/с на сокет.
Підняття до 2400 (якщо BIOS має такий страп) дало б ~12 % — на тлі вдвічі
урізаної кількості каналів це не варте ризику нестабільності на 2DPC.

### CPU

`intel_cpufreq` + governor `schedutil`, частоти 1.2–3.4 ГГц, скейлинг працює.
